# Эксперимент 23. Компиляция горячих циклов (numba), ответ тот же

**Задача (заказчик):** §38 показал, что убрать повторы мало (облако 203 → 191 мс
на кадр). Кадр упирается в две последовательные стадии — перебор ступенек
стен (трекер «заново») и кромки вида сверху; обе — циклы Python из мелких
вызовов numpy. Скомпилировать их numba. Сначала Mac, потом облако.

**Ветка:** `feature/numba` от `feature/speed-exact` (683d3ea).
**Точка отсчёта:** тег `numba-ref`. Её ответ совпадает с `speed-exact-ref`
(§38: 15/15, 9/9), поэтому эталон разработки — тот же `output/exp22_golden`.

## Главное правило

Меняется только реализация. Сверка `exp_speed.py check`: дискретное (выбор
гипотезы, число ступенек, скопления, находки) — точно, числа — до 1e-6. Не
совпало — правка откатывается или сужается до места, где совпадает.

Цель — **бит в бит**, а не «до 1e-6»: суммы повторяют попарное сложение numpy
(`pairwise_sum`, блоки по 8, делёж пополам свыше 128), степени — через `pow`,
как numpy, а не умножениями. Точность проверяется до сверки, на случайных
массивах: numba-функция против numpy-оригинала, равенство битов.

Переключатель `RAIL_JIT=0` возвращает прежний код Python — для сравнения и на
случай, если numba не установлена.

## Что компилируется (по профилю §38)

1. **Перебор ступенек стен** — `parallel_path._search_side` целиком
   (`_split_cost`, `_wmedian`, `_tukey_rho`). M4 ~22 мс, ВМ ~71 мс на кадр в
   один поток; в режиме процессов одна сторона — в процессе-помощнике.
2. **Строки полосы в `views.band_edges`** — ядро на полосу: отбор колонок у
   предсказанной оси, сдвиг, `np.add.at` в том же порядке, суммы строк.
   Предсказание оси (`polyfit`) остаётся в Python — раз на полосу (§38).
3. Остальное (RANSAC стен, по точкам) — решение по профилю после 1–2.

## Записи

- **Разработка:** 15 записей §35 (эталон `output/exp22_golden`).
- **Итоговая сверка, один раз в конце:** 8 зеркал Last_synth

## Шаги и отсечки

0. Эталон зеркал Last_synth с `numba-ref`, контрольные суммы. numba 0.60.0
   (последняя для Python 3.9, поддерживает numpy 2.0) — в `requirements.txt`.
1. `pairwise_sum` и `tukey_rho` в numba: бит в бит с numpy на длинах 0–5000
   (случайные данные, 10 000 проб). **Отсечка:** не совпало — шаг 2 делается
   только со сверкой до 1e-6, и это пишется в итог.
2. Перебор ступенек → сверка 15/15 (один поток) → замер.
3. Строки полосы → сверка 15/15 → замер.
   **Отсечка на 2 и 3:** меньше 5 мс медианы на `doubleT_obstacle` в один поток
   на M4 — откат.
4. Сверка 15/15 в режиме 4 потока + процессы; итоговая — один раз.
5. Облако: сверка против эталона Linux (§38), замер, живой прогон узла. На
   Linux numpy берёт `pow` из SVML (AVX-512) — там возможны расхождения в
   последнем бите; сверка до 1e-6 решает.

## Риски

- Компиляция при первом вызове (~1–3 с на функцию, в каждом процессе-помощнике):
  `cache=True` и прогрев в `Pipeline.warm_up` узла; в Docker — прогрев при сборке.
- `np.argsort` в numba — другая быстрая сортировка: при равных отступах кромок
  порядок весов в накопленной сумме другой. Равные отступы у вещественных
  кромок редки; сверка покажет.
