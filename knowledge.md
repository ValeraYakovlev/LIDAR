# Knowledge base: обнаружение препятствий по данным 3D-лидара (метро)

## 1. Источники

- **ТЗ**: [5. ДепТранспорта.pdf](5.%20ДепТранспорта.pdf) — хакатон "Московский транспорт". Задача: по потоку ROS 2 PointCloud2 от лидара беспилотного поезда определять наличие постороннего объекта на пути и расстояние до него.
- **Данные**: `/Volumes/T7/Dataset/` — 6 папок, в каждой один ROS 2 bag (`storage_identifier: sqlite3`, bag version 5) из одного `.db3` + `metadata.yaml`.

## 2. Требования из ТЗ (сжато)

- Среда: **Ubuntu 22.04 + ROS 2 Humble + Docker**. Любой язык/либы, если ставятся в Docker-образ.
- Стенд для проверки: i7-9700E (8 ядер), 128 GiB RAM, RTX 4070 Ti SUPER, 5.8 TB диск.
- Вход: ROS 2 bag с потоком точек лидара. Выход: `препятствие обнаружено/нет` + `расстояние до ближайшего`; плюс (опционально) положение/размеры/тип/уверенность.
- Данные для разработки ≠ финальные тестовые (обобщаемость — ключевой критерий).
- Критерии оценки: работоспособность (пропуски/ложные срабатывания), **дальность обнаружения** (300м отлично / 200м хорошо / 100м приемлемо), скорость (задержка, FPS, real-time), обобщаемость на новые проезды, техническая проработка, простота запуска (`docker build → docker run → ros2 bag play`), питч.
- Сдача: Dockerfile/образ, код, README (сборка/запуск/параметры), архитектура, описание алгоритма, эксперименты, видео.
- Подсказки от организаторов по направлениям: геометрия тоннеля как baseline + поиск отклонений, покадровые/временные изменения, аномальные кластеры, пересечение габарита, анализ рельсов — можно комбинировать простые методы вместо одной сложной модели.

## 4. Формат сообщений (sensor_msgs/msg/PointCloud2, CDR)

Схема sqlite (rosbag2): таблицы `topics`, `messages(id, topic_id, timestamp, data BLOB)`, индекс по `timestamp`. Один топик на бэг.

Все бэги содержат **только один топик** — сырой поток точек лидара, без `/tf`, одометрии, IMU и т.п. Значит позиционирование/одометрию (если понадобится) придётся получать из самого облака точек (например, ICP/сопоставление последовательных кадров) — внешних источников нет.

Layout точки (`point_step = 26 байт`, little-endian, `is_dense: false`, но реально NaN не встречалось в проверенных кадрах):

| поле | offset | тип | описание |
|---|---|---|---|
| x | 0 | float32 | метры, вбок (лево/право) |
| y | 4 | float32 | метры, **вперёд — отрицательные значения** (ось направлена в -Y) |
| z | 8 | float32 | метры, высота |
| intensity | 12 | float32 | 0–255 |
| ring | 16 | uint16 | номер канала лидара, диапазон **0–127 во всех бэгах** → сенсор 128-канальный (Hesai, судя по topic/frame_id, вероятно Hesai OT128/QT128) во всех 6 записях, несмотря на разные имена топика/frame_id |
| timestamp | 18 | float64 | пер-точечный таймстамп (u2+f8 = offset 18, влезает в 26 байт без padding) |

Numpy dtype для быстрого парсинга:
```python
dtype = np.dtype([
    ('x', '<f4'), ('y', '<f4'), ('z', '<f4'), ('intensity', '<f4'),
    ('ring', '<u2'), ('timestamp', '<f8')
])
arr = np.frombuffer(msg.data, dtype=dtype)
```

Размер кадра:
- `doubleT_obstacle`: `width=921600`, `height=1` → 921600 точек/кадр (127 rings × ~7200 азимутов), сообщение ~7.99 МБ (23 961 600 байт data).
- Остальные 5 бэгов: `width=307200` → 307200 точек/кадр (128 rings × ~2400 азимутов), сообщение ~7.99 МБ (7 987 200 байт data). Т.е. `doubleT_obstacle` снят с втрое более плотным азимутальным разрешением (или другой конфигурацией лидара/топика — иной topic name и frame_id это подтверждают).

## 5. Геометрия/система координат (по данным, не из документации)

По статистике на нескольких кадрах из каждого бэга:
- `x` (вбок): обычно в пределах примерно −20…+20 м (ширина тоннеля/путевого пространства).
- `y` (вперёд): доходит до **−200…−210 м** — то есть лидар "видит" тоннель на ~200 м вперёд, что близко к желаемому порогу "отлично" (300 м) из критериев оценки.
- `z` (высота): примерно −8…+8 м.
- `intensity`: 0–255.
- Среднее расстояние точки от сенсора ~4–7 м, p99 ~40–65 м — основная масса точек приходится на стены/путь рядом, дальние точки (стены тоннеля вдаль) — "хвост" распределения.

Т.е. ось **Y — направление движения/взгляда лидара вперёд (отрицательная полуось)**, что стоит учитывать при построении baseline-геометрии тоннеля и метрик дальности.

## 6. Наблюдение по `doubleT_obstacle` (единственный бэг с "obstacle" в названии)

Проверка кадров 0, 100, 200 из 201 не показала явной динамики (вероятно, поезд/сенсор почти неподвижен или запись короткая — 20 с). Дополнительно посчитан минимальный расстояние до ближайшей точки в узком "коридоре" прямо по курсу (|x|<1 м, |z|<2 м, y<−3 м) по всем 201 кадрам:
- Значение стабильно **~3.2–3.3 м** на всей записи (без роста/падения) — похоже на статичный объект/преграду, помещённую перед сенсором на фиксированном расстоянии, а не на препятствие, "внезапно" появляющееся в динамике.
- Это единственный бэг с явным препятствием близко (~3.3 м); остальные 5 бэгов, судя по названиям (`platform`, `pressureGate`, `switch`, комбинации `roundT`/`squareT`/`doubleT`), скорее всего репрезентируют **чистый тоннель без препятствий** (для проверки robustness/ложных срабатываний на нормальной инфраструктуре: платформы, гермозатворы, стрелки, разные формы путевых секций) — это стоит перепроверить визуально (RViz2) перед тем как полагаться на это предположение.

## 7. Высота лидара над рельсами/полом — НЕ строго постоянна

Вопрос: находится ли лидар всегда на одной и той же высоте над рельсами (важно для baseline-модели геометрии тоннеля).

Метод: для каждого сэмплированного кадра (12 кадров на бэг, равномерно по записи) бралась "коридорная" область впереди (`|x|<3м`, `y∈(-80,-10)`), из неё — нижние 15% точек по `z` как кандидаты пола, к ним методом наименьших квадратов подгонялась плоскость `z=a·x+b·y+c`. Из плоскости считались: перпендикулярное расстояние сенсора до пола (= истинная высота лидара над полом, с поправкой на наклон/качение вагона) и угол наклона плоскости пола (roll/pitch тоннеля/вагона).

Результат (12 кадров на бэг):

| Бэг | высота (перп., м): mean±std [min,max] | наклон пола: mean/max, ° |
|---|---|---|
| doubleT_obstacle | 1.783 ± 0.011 [1.765, 1.804] | 2.4 / 2.6 |
| doubleT_platform | 1.452 ± 0.062 [1.390, 1.571] | 1.2 / 4.1 |
| roundT_doubleT | 1.438 ± 0.116 [1.314, 1.679] | 0.7 / 1.7 |
| roundT_pressureGate_roundT | 1.354 ± 0.045 [1.236, 1.396] | 0.6 / 1.2 |
| roundT_squareT_pressureGate_squareT | 1.275 ± 0.111 [1.039, 1.404] | 1.2 / 3.0 |
| squareT_platform_squareT_switch | 1.379 ± 0.054 [1.239, 1.447] | 0.4 / 1.2 |

**Вывод: высота лидара над полом НЕ постоянна.**

- Внутри одной записи высота "гуляет" на несколько см — десятки см (до ~35–40 см в худшем случае, `roundT_squareT_pressureGate_squareT`: 1.04–1.40 м). Причины: качание/наклон вагона на поворотах (виражи путей дают крен пола до 2–4°, что само по себе меняет измеренную вдоль оси Z высоту), проезд стрелок/платформ/гермозатворов (сложная, не строго плоская геометрия пола рядом с этими объектами — сама оценка плоскости там менее надёжна, `fit_resid_std` растёт до 0.3–0.7м на таких кадрах против ~0.1–0.15м на обычном прямом участке).
- Единственный бэг с очень стабильной высотой — `doubleT_obstacle` (±1.1 см на 200 кадров, наклон пола тоже стабилен ~2.4°): скорее всего простой прямой участок без сложной инфраструктуры, поэтому там оценка чистая. Это косвенно подтверждает, что сам сенсор физически закреплён жёстко (не "гуляет" сам по себе) — видимая изменчивость в остальных бэгах в основном объясняется реальной геометрией пути/вагона (крен на поворотах, стрелки, платформы), а не шумом лидара.
- Средняя высота отличается и **между бэгами**: ~1.78м у `doubleT_obstacle` против ~1.3–1.45м у остальных пяти (`hesai_lidar`) — согласуется с уже отмеченным (см. §3–4) отличием конфигурации сенсора/топика в этом бэге от остальных пяти.

**Практический вывод для алгоритма**: нельзя жёстко хардкодить фиксированную высоту/плоскость пола как константу в системе координат сенсора. Baseline-модель геометрии тоннеля должна либо (а) на каждом кадре/окне кадров заново оценивать локальную плоскость пола (что и было продемонстрировано выше), либо (б) явно учитывать крен/тангаж вагона (roll/pitch) при сопоставлении с эталонной геометрией, особенно на поворотах, стрелках и платформах, где отклонение максимально.

## 8. Срезы тоннеля перпендикулярно оси глубины (Y)

Проверка: нарезка облака точек одного кадра (`roundT_doubleT`, кадр 126/251) на срезы по глубине (`depth = -y`, ширина среза 2 м), для 10 случайных срезов построен вид "в лоб" (X — вбок, Z — высота).

Наблюдения:
- **Ближняя зона (4–8 м)**: очень плотно (18–42 тыс. точек/срез). Виден сложный профиль: пол на z≈−1.3…−1.5, ступенька у x≈−1, и устойчивый вертикальный кластер точек на x≈+2, z∈[−1,1], повторяющийся в обоих ближних срезах — похоже на близкий стационарный объект инфраструктуры (опора/кабель-канал), а не шум. Такие элементы нужно учитывать в "нормальной" модели тоннеля, иначе дадут ложные срабатывания.
- **Средняя зона (14–26 м)**: чёткий, хорошо очерченный почти прямоугольный контур тоннеля (x≈[−4,+2] м, z≈[−1.5,+3] м) — самый "читаемый" диапазон для построения геометрического эталона (baseline shape).
- **Дальняя зона (>30 м)**: плотность точек резко падает (с десятков тысяч до 200–600 точек на 2-метровый срез) из-за углового разрешения лидара — на 80+ м видны только разрозненные дуги по краям. Значит на дистанциях 100–300 м (важных для критерия "дальность обнаружения") опорных точек на объект будет мало — детектор не может полагаться на плотное описание формы, скорее на паттерн редких/аномальных точек или "пропаданий" луча.
- **Профиль не одинаков и не центрирован по всей длине записи**: на 22–26 м контур смещён по X не симметрично относительно 0, а на 80+ м стены появляются в совсем других X — похоже на кривизну пути/переход между типами тоннеля (round→doubleT). Значит нельзя один раз "выучить" фиксированный эталонный профиль на весь маршрут — модель геометрии должна быть локальной (привязанной к диапазону глубины и/или обновляемой по ходу движения), а не глобальной константой.

Скрипт для воспроизведения срезов — см. рабочий venv в scratchpad-директории сессии (`rosbags` + `numpy` + `matplotlib`, `pip install rosbags numpy matplotlib`); логика: читать кадр через `rosbags.highlevel.AnyReader`, парсить `msg.data` через `numpy.frombuffer` с dtype `[('x','<f4'),('y','<f4'),('z','<f4'),('intensity','<f4'),('ring','<u2'),('timestamp','<f8')]`, бинировать по `-y` и строить `scatter(x, z)` на каждый бин.

## 9. Проверка стабильности профиля тоннеля во времени

Проверка на бэге `roundT_doubleT` (252 кадра, ~25 с): (а) отслеживалось количество точек в фиксированной "ближней колонне" (x∈[1.5,2.5], z∈[−1,1], depth∈[4,8]м, см. §8) по всем 252 кадрам; (б) для 8 кадров, равномерно разнесённых по всей записи, наложены друг на друга профили (X,Z) на нескольких фиксированных дистанциях-впереди.

Результаты:
- **"Ближняя колонна" — не часть поезда, а реальный объект инфраструктуры.** Количество точек в её области нестабильно во времени: стабильно ~12–18 тыс. на кадрах 0–90, резко скачет (0↔25тыс.) на кадрах ~95–135, затем почти полностью пропадает (0 на 101/252 кадров), с редкими короткими всплесками позже. Переходная зона (~95–135) по времени совпадает с ожидаемым переходом "круглый тоннель → развязка doubleT" (по названию бэга) — то есть нестабильность здесь объясняется реальным изменением окружения, а не шумом/движением сенсора относительно поезда. Практически: near-field (<10м) нельзя моделировать одним статичным шаблоном на всю запись.
- **Профиль тоннеля на дистанции ~15–35 м стабилен во времени.** При наложении 8 кадров, разнесённых по всей 25-секундной записи (т.е. соответствующих разным физическим участкам пути), на дистанциях 14–16, 24–26 и 34–36 м во всех кадрах виден один и тот же круглый контур тоннеля (диаметр ~6м/радиус ~3м) — форма и размер не меняются, "плавает" только горизонтальное смещение центра по X (эффект кривизны пути). На 44–46 м согласованность уже заметно хуже (шумнее, контуры перестают совпадать) — сказывается разреженность на дальности (см. §8). На 4–6 м профили разных кадров вообще не похожи друг на друга — ближняя зона зависит от конкретного места, а не общая для всей записи.

**Вывод**: диапазон ~15–35 м — лучший кандидат для геометрического baseline (круглый тоннель фиксированного радиуса с поправкой на боковое смещение/кривизну). Near-field (<10м) требует отдельной, локально обновляемой модели (там реальные изменяющиеся объекты — не шум). Far-field (>40м) ограничен разреженностью самих данных лидара, а не изменчивостью геометрии — там нужен другой класс методов (агрегация по нескольким кадрам подряд, а не покадровое сравнение с шаблоном).

## 10. Кластеризация геометрических особенностей пола (впадины/желоба) — эксперимент

Вопрос: можно ли гарантированно выделить (кластеризовать) локальное углубление в профиле пола (например, желоб/канал в центре пути, виден на срезах §8 как V-образная выемка на x≈−0.3..0, z до −1.67 при фоне пола ≈−1.3..−1.35) — нужна ли для этого ML-модель?

Эксперимент на реальных точках (`roundT_doubleT`, кадр 126, depth 3–9м, ~18.8к точек в полосе пола), железо — MacBook (Apple M4, 10 ядер, 16 ГБ RAM), библиотеки `scikit-learn` (DBSCAN) и `hdbscan`:

1. **DBSCAN на сырых точках (x,z)**: eps=0.25 → **1 кластер** на всю полосу пола (впадина не отделяется); eps=0.08 → тоже не отделяет впадину, только случайные разрывы по краям обзора (не связанные с формой впадины). Время выполнения — 0.1–0.2с на ~19к точек.
2. **HDBSCAN на сырых точках**: 87 мелких кластеров + 2797 точек "шума" — дробит непрерывную линию пола на произвольные фрагменты по локальной плотности, тоже не выделяет впадину как цельный объект. Время — 0.8с.
3. **Вывод**: плотностная/дистанционная кластеризация принципиально не может отделить такую впадину — она **физически непрерывна** с окружающим полом (нет разрыва в плотности точек между "дном впадины" и "нормальным полом"), а кластеризация группирует именно по пространственной близости/плотности, а не по отклонению формы от ожидаемой.
4. **Профильный (model-based) подход сработал**: строится эталонный профиль пола — медиана z по узким бинам x (0.08м) + сглаживание широким (1.6м, заведомо шире самой впадины) медианным фильтром; считается остаток `z − эталон`; точки с остатком `< −8см` помечаются как "не-пол" (2099 из 18799 точек). DBSCAN, применённый **только к этим уже отфильтрованным точкам**, чисто выделяет впадину отдельным кластером. Есть краевой артефакт: у границ анализируемой полосы (переход пол→стена) медианному фильтру не хватает контекста и он тоже помечает часть точек как "аномалию" — лечится ограничением зоны анализа только полосой пола (диапазон Z уже известен из §7), не подавая туда точки стен.

**Практическая рекомендация**: для типовых, известных заранее геометрических особенностей тоннеля/пути (желоба, стыки, ступени) не нужна ни generic-кластеризация, ни ML-классификатор — нужен **эталон формы + порог по остатку** (детерминированный, быстрый: доли секунды на кадр даже на CPU ноутбука, не требует разметки). DBSCAN/HDBSCAN имеет смысл использовать вторым шагом — не для поиска впадины, а для группировки уже отфильтрованных "аномальных" точек в связные объекты (отличить цельное препятствие от разрозненного шума после того, как выбросы относительно эталона уже найдены).

## 11. Эксперимент: детектор "луч vs его история" (без допущения о форме тоннеля) — ОТРИЦАТЕЛЬНЫЙ результат

Задача: тоннель не всегда круглый (см. §8 — встречаются почти прямоугольные/квадратные профили), поэтому нельзя закладывать фиксированную форму (круг) как эталон. Также `doubleT_obstacle` не годится для общей проверки — это **стоящий поезд** (см. §6, статичное препятствие на ~3.3м всю запись), а не типовая сцена. Поэтому нужно было прогнать shape-agnostic метод на всех остальных 5 бэгах целиком.

**Данные оказались полностью структурированы**: сырой массив точек одного кадра — это ровно `reshape(2400, 128)` = (азимут × кольцо) range-image (проверено на 3 подряд идущих кадрах: маска rings 0..127 повторяется идеально по строкам; азимут для фиксированного индекса строки идентичен между кадрами — привязка индекс→угол не плавает). Это открывает возможность работать с "лучом" как с постоянным идентификатором направления без пересчёта азимута на каждый кадр.

**Реализован детектор**: для каждой ячейки (азимут, кольцо) прогноз дальности на кадр t = линейная экстраполяция по двум предыдущим кадрам (`2·R[t-1] − R[t-2]`); остаток = `R[t] − прогноз`; порог `max(0.3м, 5%·прогноз)`; сработавшие ячейки группируются в объекты через связные компоненты (`scipy.ndimage.label`, 8-связность) на 2D-сетке — метод шейп-агностичен (не привязан ни к кругу, ни к квадрату).

**Производительность**: 62–183 кадр/с на Apple M4 (10 ядер, чистый NumPy/SciPy, без GPU) — все 5 бэгов (2287 кадров, ~19 ГБ сырых данных) обработаны целиком за ~20 секунд суммарно. Скорость не проблема.

**Качество — метод не работает "из коробки"**: доля кадров с крупным "аномальным" кластером (≥30 ячеек) — 58–99% по всем 5 бэгам (медиана размера крупнейшего кластера — от 114 до 1614 ячеек, максимумы — 24–38 тыс. ячеек). Это заведомо ложные срабатывания почти на каждом кадре, метод в текущем виде непригоден.

**Причина установлена экспериментально — эгомотion, а не шум формы**: на `doubleT_platform` (поезд подъезжает к платформе и останавливается) посчитан прокси скорости — медиана `|R[t]−R[t-1]|` по валидным ячейкам. Кривая прокси-скорости и кривая размера ложного кластера идут почти синхронно (корреляция ≈0.55) и **обе падают к нулю к кадру ~165**, ровно когда поезд останавливается (после этого — почти идеальная тишина, кластеры пропадают). Объяснение: при движении поезда один и тот же индекс луча (азимут+кольцо) в кадрах t-1/t/t-2 физически указывает на разные точки тоннеля (сенсор сместился/повернулся), поэтому простая линейная экстраполяция по лучу систематически ошибается — и ошибка растёт с скоростью. В датасете нет одометрии/`/tf` (см. §3), которая могла бы скомпенсировать это смещение.

**Вывод**: 
- Наивное покадровое сравнение "луч сейчас vs луч раньше" (метод из подсказки ТЗ "изменения в пространстве между последовательными кадрами") **требует предварительной компенсации движения** (scan-to-scan регистрация/ICP между кадрами) — без неё он непригоден на подвижном поезде, что подтверждено на всех 5 бэгах, а не только теоретически.
- Компенсация движения — отдельная нетривиальная подзадача (одометрии в данных нет, придётся оценивать движение по самому облаку точек).
- До реализации компенсации движения надёжнее опираться на **внутрикадровый** подход из §7–10 (локальный эталон пола/стен по одному кадру + остаток), который принципиально не зависит от формы тоннеля и не сравнивает кадры между собой — там ложных срабатываний такого масштаба не было.
- Межкадровый анализ стоит переиспользовать позже — не для покадрового diff по лучу, а либо (а) поверх уже компенсированного движения, либо (б) для сглаживания/подтверждения уже найденных внутрикадровых кандидатов на препятствие во времени (объект должен быть виден несколько кадров подряд, а не мелькать один раз).

## 12. Рабочий внутрикадровый (shape-agnostic) детектор — v2, провалидирован на известном препятствии

После отрицательного результата §11 (межкадровый метод ломается из-за эгомоушна) собран **однокадровый** детектор, не сравнивающий кадры между собой и не предполагающий форму тоннеля (ни круг, ни квадрат) — только локальную гладкость вдоль азимута в пределах одного кольца лидара. Разрабатывался и тестировался итеративно на `doubleT_obstacle` (единственный бэг с реальным известным препятствием — стоящий поезд на ~3.3м, см. §6), железо — Apple M4, 10 ядер, чистый NumPy/SciPy.

### Пайплайн (v2)

1. **Range-image**: кадр `reshape(n_az, 128)` — данные полностью структурированы (азимут×кольцо), подтверждено на 3 бэгах с разным n_az (2400 и 7200), привязка индекс-строки к реальному углу не плавает между кадрами (см. §11).
2. **Локальный эталон**: медианный фильтр по азимуту (окно ~8°, только внутри одного кольца, `mode='wrap'`) → `ref`.
3. **Остаток**: `residual = range − ref`; порог `max(0.15м, 5%·ref)`; флаг "аномалия" = точка ближе эталона больше чем на порог.
4. **Density-gate (ключевой фикс №1)**: без него — 56 011 "аномальных" ячеек и тысячи кластеров на кадр, в основном ложные — из-за разреженных/прерывистых валидных точек на крайних кольцах (около потолка/пола обзора), где эталон постоянно "спотыкается" о переходы валид/невалид. Фикс: считать аномалию только там, где локальная плотность валидных точек в том же окне >85% (`scipy.ndimage.uniform_filter`). Снижает число ложных ячеек в ~5 раз (56011→11049).
5. **Морфологическое объединение (фикс №2)**: даже после density-gate реальное препятствие дробится на ~1300 мелких кусков (2–20 ячеек) — метод по кольцам независим, соседние кольца не "видят" друг друга. Фикс: `binary_dilation` (9×5) + `binary_closing` (15×15) перед связной разметкой — собирает разрозненные по кольцам фрагменты края объекта в один связный блок. После фикса препятствие — доминирующий кластер (>6000 ячеек, следующий по размеру — на порядок меньше).
6. **Финальная дистанция**: не по "аномальным" точкам (это в основном только край/контур объекта), а минимум по **всем сырым точкам** внутри найденной 2D-области кластера — так получаем реальную ближайшую точку объекта, а не точку его силуэта.
7. **Self-mask (фикс №3)**: без него ближайшим "объектом" в каждом кадре стабильно оказывалась точка на x≈0.95м, z≈0м, range≈0.96м — идентичные координаты кадр в кадр (в отличие от реального препятствия, которое было бы на разной x/z при приближении) → это собственная конструкция поезда/крепление лидара, а не тоннель. Исключена жёстким боксом (x∈[0.6,1.3]м, z∈[-0.35,0.35]м), найденным визуальным анализом первых кадров.

### Результат валидации (все 201 кадров `doubleT_obstacle`)

- Детекция в **201/201 кадров (100%)**.
- Дистанция до препятствия: медиана **3.41м**, 10–90 перцентиль **3.23–3.42м** — совпадает с независимой оценкой §6 (~3.2–3.3м, посчитана другим методом — простой минимум в узком коридоре).
- Есть ~10 кадров (из 201) с занижением дистанции до 1.97–2.4м (кадры ~26–34 и ~145–157) — вероятно неполное исключение self-структуры жёстким боксом (её положение чуть смещается между кадрами и иногда вылезает за границы бокса); требует уточнения self-mask, не расследовано до конца.

### Известные ограничения (честно, не приукрашено)

- **Скорость**: 1.45–1.9 кадр/с на `doubleT_obstacle` (n_az=7200) на чистом NumPy — ниже реального времени (10Гц). На остальных 5 бэгах (n_az=2400, втрое меньше) ожидается ~3× быстрее, но не измерено. Нужна оптимизация (векторизация по кольцам разом, C++/GPU) для реального стенда.
- **Self-mask захардкожен** из визуального анализа одного бэга, не из отдельной калибровочной процедуры — не факт, что переносится на другие бэги/сенсоры без переподбора.
- **Не проверен false-positive rate** на "чистых" бэгах (аналогично тесту §11 для temporal-метода) — это естественный следующий шаг: прогнать этот же v2-пайплайн на всех 5 "нормальных" бэгах целиком и посмотреть, не ловит ли он лишнего (стыки тюбингов тоннеля, кабели, переходы round→square и т.п., которые уже выявляли ложные срабатывания в первой версии до фиксов).
- Пороги (окно 8°, density-gate 85%, min_cluster 20 ячеек) подобраны вручную по одному бэгу — не оттюнены систематически.

Скрипт: `spatial_detector_v2.py` в scratchpad-venv сессии (`rosbags`+`numpy`+`scipy`).

## 13. Проверка гипотезы "рельсы = приподнятые плечи по краям центральной выемки"

Новое направление (обсуждение, не связано с temporal/spatial-детекторами §11-12): вместо геометрии тоннеля (стены/потолок, которая сильно варьируется, §8) — искать **рельсы и строить габарит движения поезда** относительно них. Габарит подвижного состава — фиксированная физическая величина, не зависящая от формы тоннеля вокруг; это прямо снимает проблему "тоннель не всегда круглый" (§8-9) и потенциально снимает проблему повторяющейся инфраструктуры (§9) — она по определению должна быть вне габарита.

В §10 была найдена V-образная выемка в полу (x≈−0.7…+0.1, глубина до -1.67 против пола ≈-1.3…-1.35) и первоначально интерпретирована как дренажный канал. Гипотеза для проверки: **это не канал, а промежуток МЕЖДУ рельсами — сами рельсы — приподнятые "плечи" по краям этой выемки.**

**Метод проверки**: на срединном кадре каждого из 5 "чистых" бэгов (без `doubleT_obstacle`) — серия срезов по глубине от 3м до 130м с растущим шагом (компенсирует падение плотности с расстоянием), в каждом срезе: адаптивная полоса пола (1–45 перцентиль Z в коридоре |x|<4м), медианный профиль Z(X) с шагом 5см, поиск глобального минимума и проверка наличия "плеч" (подъём Z по обе стороны от минимума).

**Результат — гипотеза подтверждена, с чёткой границей применимости**:
- **До ~30–40м: выемка присутствует стабильно во ВСЕХ 5 бэгах**, независимо от формы тоннеля/наличия платформы/гермозатвора/стрелки. На 4–5м — чёткий резкий V-профиль глубиной ~15–35см, почти идентичной формы во всех пяти записях, несмотря на то что вся остальная геометрия (стены/потолок) в этот момент кардинально разная. Сильное подтверждение: это инвариантный к тоннелю признак, а не совпадение.
- **После ~40–50м профиль разваливается в шум** — не потому что физическая геометрия меняется, а из-за катастрофического падения плотности точек (та же причина, что в §8): на срезе 65–80м всего 500–1100 точек на весь диапазон |x|<4м при толщине среза 15м (против 15–60 тыс. вблизи) — ни в одном из 5 бэгов не видно узнаваемой V-формы на этой дистанции, только шум.
- Числовая метрика "глубина выемки vs дистанция" подтверждает то же самое: стабильные ~15–35см до ~25–30м, дальше — скачки на десятки-сотни см (артефакт шума на разреженных данных, не реальный сигнал).

**Вывод**: признак "рельсы = плечи вокруг центральной выемки" — рабочий и надёжный геометрический инвариант, не зависящий от формы тоннеля, но **только на дистанции до ~30–40м напрямую по одному кадру**. Для дальней зоны (важной для критерия "300м = отлично", §ТЗ) чистая покадровая геометрическая детекция рельсов не сработает по тем же причинам разреженности, что и раньше — нужен не другой признак, а трекинг/экстраполяция уже найденного близко centerline рельсов, а не независимый поиск с нуля на каждой дальней дистанции.

**Открытые вопросы для дальнейшей проверки** (не проверялись в этом эксперименте): точная ширина колеи по позиции "плеч" (не просто ширина самой выемки — нужно отдельно локализовracте пики подъёма по бокам), использование intensity как дополнительного признака (рельс — металл, должен быть ярче балласта/бетона), устойчивость центра выемки (x_min) как индикатора кривизны пути в кадре.

## 15. Геометрия тоннеля в координатах пути (rail-guided) — рабочий метод

Постановка от §13 доведена до конца: рельсы используются не сами по себе, а как **опора, относительно которой ищется всё остальное**.

### Почему прежние детекторы стен ошибались

Прежние методы (`walls.find_wall_positions` — ближайшее к центру плотное скопление; `walls.combined_wall_fit` — объединение трёх наборов кандидатов) искали стену **независимо в каждом срезе, в координатах сенсора**. У одиночного среза нет признака "это именно стена": между путём и стеной есть контактный рельс, кабельные лотки, настил служебного прохода, а сама стена местами уходит в нишу или раскрывается в соседний путь. Поэтому ошибка среза ничем не ограничена — "ближайшее скопление" систематически цепляло лоток в метре от центра, "самое дальнее" улетало в проём.

Второй, более важный дефект был в **метрике**: кадр считался пройденным, если подгонка получилась ГЛАДКОЙ. Гладкость не отличает верную стену от неверной — прямая, проведённая через кабельный лоток, ровно так же гладкая. Отсюда и уживались 90% на замороженной выборке с картинками, где линия идёт заметно внутри тоннеля.

### Метод

1. **Опора по рельсам (ближняя зона).** `find_groove_and_rails` по срезам до 20 м — там точек на порядок больше и желоб виден надёжно; срезы с колеёй, отличающейся от медианы более чем на 25 см, отбраковываются как промахи детектора (колея физически постоянна). По оставшимся — RANSAC-подгонка оси пути (прямая/дуга) и линейного профиля уровня головки рельса `z_f(d)`. Дальняя зона получается экстраполяцией, а не независимой детекцией.
2. **Криволинейные координаты пути**: `u = (x − x_ось(d))·cos(курс)`, `v = z − z_f(d)`. Множитель `cos(курс)` делает `u` расстоянием по нормали к пути: на повороте срез постоянной глубины режет тоннель наискось.
3. **Клиренс-полоса `v = 0.2…1.1 м`** над головкой рельса — выбрана по данным, а не наугад. Настил платформы лежит на `v ≈ +1.2 м` и уходит вбок на 4–5 м; лотки и своды — ещё выше. Прежняя широкая полоса (`floor+0.3…+2.5`) неизбежно захватывала их вместо стены. В узкой полосе остаётся ровно то, что образует боковую границу: вертикальная грань стены либо торец платформы. Это же и полоса, важная для габарита.
4. **Оценка границы по срезу** — 97-й перцентиль `|u|` (не максимум: ловит единичный выброс; не пик плотности: ловит самую отражающую поверхность, часто лоток перед стеной).
5. **Согласование по всему кадру, одной формой на обе стены.** Медиана ближних срезов задаёт стартовые полуширины, дальше — попеременное уточнение "модель → какие срезы ей соответствуют (окно ±0.55 м) → модель".

### Какой формулой описывается изгиб

Трасса железнодорожного пути состоит из трёх элементов: прямая, круговая кривая постоянного радиуса `R` и переходная кривая (клотоида), где кривизна нарастает линейно по длине. В окне одного кадра (до ~42 м) угол поворота не превышает ~8°, поэтому законно малоугловое приближение, и круговая кривая описывается параболой:

```
x(d) = c + b·d + a·d²,   R = 1/(2|a|)
```

Клотоида добавила бы кубический член `d³/(6RL)`, но на базе 40 м он неотделим от шума подгонки — в пределах кадра клотоида и дуга неразличимы, поэтому дуга здесь и есть правильный уровень детализации.

Ключевое: **обе стены и путь между ними — одна и та же кривая, сдвинутая вбок**. Поэтому форма подгоняется ОДНА на обе стороны сразу, а стороны отличаются только постоянной полушириной:

```
s(t) = α·t² + β·t,  t = d/40      — увод оси тоннеля от прямой опоры по рельсам
o_Л(d) = W_Л − s(d)               — смещение левой границы (положительное)
o_П(d) = W_П + s(d)               — смещение правой границы
x_{Л,П}(d) = x_опора(d) ∓ o_{Л,П}(d)/cos(курс)
```

Все четыре параметра `(α, β, W_Л, W_П)` входят линейно — это обычный МНК, а не перебор. Общие `α, β` физически запрещают стенам разъезжаться "домиком" (независимая подгонка сторон давала именно это) и позволяют набрать кривизну по точкам с обеих сторон сразу.

**Кривизна берётся со стен, а не с рельсов.** Рельсы надёжно детектируются только вблизи (до ~20 м), а на такой базе поворот неотличим от шума: при `R=300 м` стрелка прогиба на 17 м — 12 см, меньше разброса детектора. Стены видны на всю глубину и с обеих сторон, и на базе 40 м тот же поворот даёт уже 0.67 м. Поэтому ось по рельсам используется как **прямая** опора (положение и курс вблизи), а кривизну определяют стены.

**Прямая или дуга — решается по данным.** Лишний свободный параметр всегда чуть уменьшает невязку, поэтому "с дугой лучше" само по себе ничего не значит — иначе модель находит поворот на любом замусоренном кадре. Дуга принимается при трёх условиях сразу: невязка падает минимум в 1/0.85 раза, изгиб превышает невязку подгонки вчетверо (`α` — это прямо увод стены вбок в метрах на 40 м, его и сравниваем с невязкой), и `R ≥ 120 м` (круче метро не поворачивает). На выборке дуга выбирается примерно в каждом шестом кадре, с радиусами 236–908 м — правдоподобный диапазон для метро.

### Метрика (честная, привязанная к точкам)

- **coverage** — доля срезов, где стена реально наблюдается (рядом с предсказанным положением есть точки). Ловит кривую, проведённую через пустоту.
- **leak** — доля точек ЗА стеной дальше 30 см, считается ВНУТРИ каждого среза и усредняется по срезам. Настоящая стена непрозрачна. Усреднение именно по срезам: плотность падает как 1/r², и доля по всем точкам сразу мерила бы только ближние 5 метров — одна ниша у самого поезда утаскивала её к 0.6 при правильной стене на всей остальной глубине.

Порог: `coverage ≥ 0.70`, `leak ≤ 0.15`, смещение в 1.2…6.5 м. Одной меркой меряются все три метода.

### Проверка на целом прогоне

`make_run_gif.py` прогоняет метод по всем кадрам одной записи подряд и собирает GIF вида сверху с лентой кривизны. Это отдельная проверка от покадровой метрики: по одному кадру нельзя отличить настоящий поворот от шума подгонки, а на ленте поворот виден как сплошной участок одного знака.

`roundT_pressureGate_roundT` (268 кадров, 26.7 с) оказался S-образным: дуга распознана в 84 кадрах из 134, сначала устойчивый поворот **налево** (кадры ~90–175, `R ≈ 635 м`), затем устойчивый **направо** (~190–265, `R ≈ 540 м`), между ними и по краям — прямая. Радиусы держатся в одном диапазоне на десятках последовательных кадров, которые обрабатываются независимо друг от друга — это независимое подтверждение, что кривизна измеряется, а не подгоняется.

Единственный дефект на ленте — одиночные всплески на кадрах ~55–65 (зона гермозатвора), окружённые нулями. Настоящий поворот не может длиться один кадр, так что это ложные срабатывания; временное сглаживание по соседним кадрам их снимет, но в покадровом методе их видно честно.

Сводка по всем шести записям (шаг подобран под ~150 кадров GIF):

|---|---|---|---|---|

**Важная находка: в `roundT_squareT_pressureGate_squareT` опора не строится на первых ~160 кадрах записи подряд** (это и есть все 46 отказов — они не разбросаны, а идут сплошным куском в начале). На покадровых выборках это выглядело как 3–12% редких отказов, и только просмотр прогона целиком показал, что отказы кластеризуются: треть записи не обрабатывается вообще.

При этом на этих кадрах **стены в облаке отлично видны** — не хватает именно рельсов: облако там заметно разрежено у пола. То есть узкое место не в поиске стен, а в жёстком требовании опоры по рельсам в каждом кадре независимо. Напрашивающееся продолжение — переносить опору с предыдущих кадров (путь между соседними кадрами меняется мало), тогда достаточно найти рельсы хоть где-то в записи. Здесь это не делалось: методика покадровая, а временной трекинг — отдельный шаг.

### Что остаётся неверным (честно)

- **Нет опоры по рельсам**: 3 кадра из 100 на dev, 6 из 51 на hidden. Проверено отдельно — желоб там виден в 1–4 срезах с несогласованными центрами, то есть данных действительно нет. Метод отказывается вместо того, чтобы выдать произвольную стену.
- **Платформа и стрелка**: боковая граница там меняется скачком (торец платформы ~1.7 м, стена за ней ~2.3 м), одна модель описывает либо то, либо другое — отсюда `coverage ≈ 0.55…0.67` на таких кадрах.
- **Расширяющиеся участки** (двухпутный `roundT_doubleT`, раскрытие перед гермозатвором): там одна стена уходит вбок, а вторая стоит на месте. Модель параллельных стен такого по построению не описывает — и это сознательный размен: свободный член "расширения" вернул бы артефакт расхождения "домиком", который и был главной претензией к независимой подгонке. Метрика показывает такие кадры честно, вместо того чтобы подгонять под них форму.
- **Локальные раскрытия** (ниша у самого поезда): тоннель действительно шире на 4–7 м и уже дальше. Для задачи поиска препятствий это скорее признак аномалии, чем дефект геометрии.

## 16. Увязка рельсов с изгибом тоннеля + кусочная ширина

Продолжение §15. Три изменения, каждое измерено отдельно.

### Методика: заморожен ПРОГОН, а не кадры

Прежние выборки — случайные кадры из всех записей, в том числе тех, на которых алгоритм и доводился. Соседние кадры одной записи почти одинаковы, поэтому такая выборка отвечает на вопрос «работает ли на похожих кадрах», но не на «переносится ли на незнакомый участок».

Здесь отложена **запись целиком**: `roundT_squareT_pressureGate_squareT` (`validation_run.json`, 137 кадров с шагом 4) — самая трудная из чистых. Разработка шла на `dev_runs.json` (4 оставшихся чистых прогона целиком). `doubleT_obstacle` исключён из обоих: стоящий поезд перекрывает тоннель, геометрия за ним не наблюдаема.

### Изменение 1: профиль пола по всей глубине

Уровень пола подгонялся только по срезам, где детектор нашёл рельсы, а они сосредоточены в ближней зоне — дальше профиль экстраполировался с базы 3–20 м. Теперь он строится по всем срезам с рельсами, а если рельсов нет вовсе — из самого облака: форму даёт низкий перцентиль `z` у оси (повторяет `shoulder_z` со стандартным отклонением 2–8 см), а смещение на глубину желоба калибруется в кадре по самому населённому уровню среди нижних точек. Плюс грубый курс по стенам, когда рельсов нет.

Результат: кадры без опоры исчезли полностью (было 46 из 137 на валидации, 1 из 267 на dev).

### Изменение 2: рельсы и стены — одна система МНК

Рельсы — наблюдение той же кривой, что и стены, только самой оси. Раньше они работали отдельным предварительным шагом: подгонялась прямая, и на повороте её наклон оказывался наклоном **хорды**, а не касательной, — ошибка уходила в форму стен. Теперь в одну систему идут строки трёх видов: `u_рельс = s(d)`, `o_Л = W_Л − s(d)`, `o_П = W_П + s(d)`, где `s(t) = α·t² + β·t + γ`. Свободный член `γ` определим только при наличии рельсов; без них сдвиг оси неотличим от согласованного изменения полуширин.

В подгонку берутся только рельсы ближе 15 м — дальше детектор регулярно промахивается. Заодно дальние детекции остаются **отложенной проверкой оси**: предсказание кривизны по стенам сверяется с тем, где рельсы реально оказались, без их участия в подгонке.

Результат: медиана ошибки оси на отложенных рельсах **0.050 → 0.037 м** (−26%) при неизменной метрике стен. Метрика стен этого показать не может — она про границы, а не про ось; поэтому увязка и потребовала отдельной метрики.

### Изменение 3: кусочно-постоянная полуширина

Тоннель не одной ширины на весь кадр: у станции граница — торец платформы (~1.8 м), за её концом — стена позади (~2.4 м), разрыв в полметра; перед гермозатвором тоннель раскрывается. Одно число этого не описывает, и именно такие кадры не проходили порог.

Форма `(α, β, γ)` остаётся **общей** — стены по-прежнему не могут разъехаться «домиком», меняться разрешено только расстоянию до них. Разрыв допускается при трёх условиях: участок не короче 3 срезов, скачок не меньше 25 см, и разрыв снижает среднюю `|невязку|` хотя бы в 1/0.8 раз. Считается по медиане и средней `|невязке|`: у ступени соседний участок — выброс огромной величины, и квадратичная мера размазала бы границу.

Два тонких места, на которых это сначала не работало: сегментировать надо по **всем** срезам, а не по инлайерам (модель с одной шириной как раз и объявила выбросами всё по ту сторону ступени), и после сегментации надо **пересеивать маски по участкам**, иначе у нового участка не остаётся инлайеров и его ширина вырождается в ноль.

### Результат на dev (267 кадров, 4 прогона)

| разрывов ширины | обе стены | хотя бы одна | ось: медиана | 90% |
|---|---|---|---|---|
| 0 (как в §15, но с новым полом) | 81.6% | 99.3% | 0.037 м | 0.221 |
| 1 | 88.0% | 99.6% | 0.032 м | 0.179 |
| **2 (выбрано)** | **91.0%** | **100%** | 0.032 м | 0.229 |

Базовая линия §15 на том же наборе — **80.9%**. Прирост идёт на всех четырёх прогонах сразу (платформа 68→77%, двухпутный 79→94%, гермозатвор 94→99%, стрелка 85→96%), а не на одном — значит это не подгонка под отдельные кадры.

### Слепая проверка на отложенном прогоне

`roundT_squareT_pressureGate_squareT` в разработке не участвовала; проверка сделана один раз, после того как все решения были приняты по dev.

| | было (§15) | стало |
|---|---|---|
| обе стены | 59.9% | **97.8%** (134/137) |
| хотя бы одна | 65.0% | **100%** |
| кадров без опоры | 46 из 137 | **0** |
| ошибка оси на отложенных рельсах | — | 0.041 м (90-й перц. 0.091 м) |

Отложенный прогон вышел выше dev (97.8% против 91.0%) не потому, что он лёгкий: по прежней метрике он был самым трудным именно из-за 46 кадров без опоры. Когда опора перестала зависеть от детекции рельсов, оказалось, что геометрически он простой — прямой перегон с гермозатвором, без платформ. А dev вниз тянет `doubleT_platform` (77%), где граница ступенчатая по-настоящему.

Ошибка оси на отложенных рельсах — 4 см при 90-м перцентиле 9 см. Эти рельсы в подгонке не участвовали, так что это честное измерение: кривизна, снятая со стен, действительно предсказывает, куда уходит путь.

### Что остаётся неверным

- `doubleT_platform` — 77%: у станции боковая граница меняется не ступенькой, а сложнее (платформа, за ней проём, за ним стена), и двух разрывов не всегда хватает.
- Дальний конец кадра на раскрытиях (30–40 м) описывается одной полушириной плохо: там уже не стена, а открытое пространство, и «граница» перестаёт быть определённой величиной.
- Всё по-прежнему покадрово: соседние кадры не связаны, поэтому одиночные ложные дуги (§15) никуда не делись. Временной трекинг — следующий шаг, здесь он не делался.

## 17. Связь кадров между собой и предел дальности

Эксперимент проверял три идеи. Две не подтвердились — и это тоже результат.

### Методика

Заморожен целиком прогон `doubleT_platform` (`validation_run_v2.json`, 173 кадра с шагом 2) — самый трудный по метрике §16 (74% против 94–99%). Разработка шла на `dev_runs_v2.json` (4 остальных чистых прогона, 544 кадра). Кадры в обоих наборах идут **подряд** с постоянным шагом: временной трекинг требует последовательности, случайная выборка кадров для него бессмысленна.

Оговорка: `doubleT_platform` участвовал в разработке §16, так что полностью девственным он не является. И валидация здесь использована **дважды** (см. ниже) — второй результат уже не слепой в строгом смысле.

### Идея 1: отсекать точки дальше 3 м вбок там, где распознан желоб — ОТВЕРГНУТА

Замысел: вблизи поезда боковая граница физически не может быть дальше трёх метров, всё остальное — настил платформы, ниша или соседний путь, то есть помеха.

Замер на dev:

| ворота | обе стены | на двухпутном прогоне |
|---|---|---|
| выключены | **96.5%** | 94% |
| 3 м | 92.8% | 86% |
| 4 м | 91.5% | 75% |

Причина провала выяснилась сразу: полоса высот `v = 0.2…1.1 м` (§15) уже отсекает ровно то, ради чего ворота задумывались — настил платформы лежит выше. А вот там, где тоннель действительно раскрыт (двухпутный участок, 6.5 м с самого начала), ворота срезают настоящую стену и создают выдуманный скачок ширины на глубине ворот. Мягкий откат «если внутри ворот опоры нет — берём полный коридор» помогает не всегда: достаточно любой помехи в пределах трёх метров, чтобы откат не сработал.

Код оставлен (`near_gate=` в `fit_tunnel_geometry`), но по умолчанию выключен.

### Идея 2: увеличить глубину подгонки — ОТВЕРГНУТА частично

Замер показал, что стена наблюдаема примерно до 50–60 м (на 40–50 м ещё 80–150 точек на сторону), тогда как срезы кончались на 42 м. Расширение до 62 м на dev оказалось нейтральным в среднем (96.7% → 96.5%), но на **станционном** прогоне стоило 97% → 95%: за 40 м у станции начинается открытое пространство, и дальние разрежённые срезы описывают уже не стену.

Поэтому глубина подгонки возвращена к 42 м, а вопрос «докуда видно» решён отдельно: `REACH_DEPTH_BINS` зондируют 42–100 м **только на наличие точек у предсказанной границы**, не участвуя в подгонке. Ответ: **граница уверенно наблюдается до ~45 м**, дальше точек в клиренс-полосе уже не хватает на локализацию. На виде сверху этот предел нарисован явно: сплошная линия — измерение, пунктир — экстраполяция.

### Идея 3: связать кадры между собой — ПОДТВЕРЖДЕНА, но не с первой попытки

Первая реализация — ограничение скорости изменения («за кадр α не может измениться больше чем на столько-то»). На dev выглядела отлично: дрожание кривизны втрое меньше при неизменной метрике стен. На отложенном прогоне — провал: 74.0% → **68.8%**, точность оси хуже вдвое (0.032 → 0.064 м).

Причина принципиальная: **ограничитель не гасит ошибку, а растягивает её**. Один неверный кадр сдвигает состояние, и следующие кадры, даже правильные, не могут вернуться быстрее разрешённого шага — одиночный выброс превращается в плато. На dev это не проявилось, потому что там мало кадров, где подгонка резко ошибается; станция — как раз такой случай.

Заменено на медиану кривизны по короткому окну. Выброс не попадает в середину выборки и исчезает целиком, состояние при этом не смещается ни на шаг.

| конфигурация | обе стены | хотя бы одна | ось | скачок α | мельканий |
|---|---|---|---|---|---|
| без трекинга | 96.7% | 99.8% | 0.034 | 0.426 | 26/536 (4.9%) |
| медиана, окно 3 | 97.1% | 100% | 0.040 | 0.180 | **0** |
| **медиана, окно 5** | 96.9% | 100% | 0.042 | 0.128 | **0** |
| медиана, окно 9 | 97.1% | 100% | 0.044 | 0.106 | **0** |

«Мелькание» — кадр, чей тип отличается от **обоих** соседей. Тоннель не может повернуть и выпрямиться за один кадр, так что это всегда ошибка подгонки, и её доля — прямая мера покадровой неустойчивости. Она обнулилась при любом окне.

Взято окно 5: выброс гасится, даже если ошиблись два кадра подряд (у гермозатвора так бывает), а плата — 2 мм точности оси.

Заодно прошлые полуширины передаются в подгонку как стартовое приближение — но только если точки текущего кадра их подтверждают, иначе на въезде в станцию подсказка утащила бы согласование в пустоту.

### Итог

| | до эксперимента | после |
|---|---|---|
| dev, обе стены | 96.7% | **96.9%** |
| dev, хотя бы одна | 99.8% | **100%** |
| dev, мельканий | 4.9% | **0%** |
| dev, скачок α | 0.426 | **0.128** |
| отложенный прогон, обе стены | 74.0% | **74.6%** |

Валидация использована дважды: первый раз — на варианте с ограничителем (68.8%, регресс), второй — после замены на медиану (74.6%). Второй результат поэтому не полностью слепой; диагностика причины провала делалась на dev, а не на нём.

Точность не выросла — она и не могла: метрика стен покадровая, а трекинг чинит связность между кадрами. Выросла именно связность, и на GIF это видно прямо: кривизна больше не дёргается на прямых перегонах.

## 18. Детектор рельсов по колее, а не по выемке

Разбор конкретного кадра, на котором ось пути «прыгала», привёл к самой крупной
ошибке в основании всего метода.

### Что было видно

На `roundT_squareT_pressureGate_squareT` кадры 160–176 шли **вовсе без рельсов**,
а на кадре 168 детектор находил три среза с центрами x ≈ −1.4 и колеёй
0.85–1.40 м. Прямая по ним дала опору со сдвигом −2.57 м и наклоном +0.0625;
модель компенсировала это полуширинами **−0.30** и 4.63 (отрицательная ширина —
бессмыслица). Стены при этом вставали правильно, `cov=1.00 leak=0.00`, поэтому
метрика стен ошибку не замечала вовсе.

### Причина

Срезы перпендикулярно оси Y (`plot_cross_sections.py`) показали всё сразу: на
этом участке путь уложен на **плитное основание**. Пол между рельсами плоский,
выемка 3–5 см, а детектор из §13 требует ≥6 см — и отказывает на каждом срезе.
Сами рельсы при этом видны отлично: два пика по 10–15 см на расстоянии ~1.65 м.

Хуже того, единственным достаточно глубоким провалом в пределах `|x| < 4 м`
оказывается щель между крайним рельсом и стеной, и детектор принимал за путь её.

То есть признак «рельсы = плечи вокруг V-образной выемки» (§13), проверенный
тогда на средних кадрах пяти записей, **держится не везде**: глубина выемки
зависит от типа основания пути, а не от геометрии колеи.

### Что сделано

Опорой стала **колея**: расстояние между головками рельсов — константа сети
(по замерам 1.55–1.70 м на всех записях), тогда как выемка — свойство основания.
`find_rails_by_gauge` ищет пару пиков профиля на нужном расстоянии, выбирая по
выраженности и близости к ожидаемой колее. `find_rails` пробует сначала прежний
детектор, а при отказе **или неправдоподобной колее** — новый.

Абсолютная проверка колеи нужна отдельно от согласования срезов между собой:
когда детектор находит «путь» шириной 0.85 м, это не шум, который усреднится, а
систематический промах на щель у стены, и трёх таких срезов хватает, чтобы
увести опору на метры.

На кадрах 160–176 стало 13 срезов из 13 вместо 0–3, колея 1.65, центры −0.00…−0.23.

### Отсечение по стенам прошлого кадра

Идея: между кадрами поезд проезжает единицы метров, значит стены прошлого кадра
— надёжная граница «здесь тоннель кончается», и всё снаружи можно выбросить.

Замер показал, что применять её надо **только к детектору рельсов**:

| конфигурация | обе стены | на двухпутном прогоне |
|---|---|---|
| покадрово | 98.0% | 94% |
| маска везде (и на поиск стен) | 94.5% | **84%** |
| маска только для рельсов | 97.8% | 94% |

Маска на поиске стен работает **храповиком**: стоит одному кадру занизить стену,
и следующий физически не может увидеть дальше — точки оттуда уже выброшены. Это
та же болезнь, что была у ограничителя скорости в §17, только через другой
механизм. Детектору рельсов маска, наоборот, необходима: он ищет провал профиля
вблизи, где прошлая граница заведомо надёжна, и именно там щель у стены его и
сбивала.

Отдельно: метрики считаются по **полному** облаку, а подгонка — по отсечённому.
Иначе отсечение аттестует само себя — выброшенные точки перестают попадать в
«утечку за стену», и `leak` обнуляется независимо от того, верна стена или нет.

### Ошибка визуализации

На виде сверху рисовалась **опорная** ось (прямая по рельсам), а не итоговая.
Когда рельсы находились плохо, опора улетала вбок, а модель компенсировала это
полуширинами — на картинке это выглядело диким прыжком оси при правильных
стенах. Теперь рисуется итоговая ось (`tunnel_center_coeffs`).

| | до §18 | после |
|---|---|---|
| dev, обе стены (покадрово) | 96.7% | **98.0%** |
| dev, обе стены (с трекингом) | 96.9% | **97.8%** |
| dev, мельканий | 0% | 0% |
| **отложенный прогон, обе стены** | 74.6% | **83.8%** |
| отложенный, ось (90-й перцентиль) | 0.262 м | **0.141 м** |
| отложенный, кадров с рельсами | 167/173 | **173/173** |

Прирост на отложенном прогоне (+9.2 пункта) больше, чем на разработочном, —
это признак того, что чинилась настоящая общая ошибка, а не подгонка под dev.
