# Обнаружение препятствий на пути поезда метро по 3D-лидару

Хакатон «Московский транспорт», кейс «Система обнаружения посторонних объектов
для беспилотных поездов в тоннеле метро по данным 3D-лидара» (ТЗ —
[docs/ТЗ_ДепТранспорта.pdf](docs/ТЗ_ДепТранспорта.pdf)).

ROS 2-узел принимает поток облаков точек лидара (`sensor_msgs/PointCloud2`) и на
каждый кадр отвечает: **есть ли на пути поезда препятствие и на каком
расстоянии** (вдоль пути, в метрах). Всё работает в Docker (Ubuntu 22.04 +
ROS 2 Humble).

**Идея.** Объекты не классифицируются. Узел строит по кадру геометрию тоннеля —
ось пути, стены, крен, профиль пути по высоте — и ставит вдоль пути габарит
кузова вагона 81-717. Препятствие — всё, что попало внутрь габарита и
удержалось на своём месте в тоннеле 3 кадра из 5. Такой подход не требует
размеченных примеров препятствий и одинаково ловит человека, коробку или блок.

## Быстрый запуск

Нужны Docker, git и папка записи ROS 2 bag (`metadata.yaml` + `.db3`).

```bash
# 0. код решения
git clone https://github.com/ValeraYakovlev/LIDAR.git && cd LIDAR

# 1. сборка (все зависимости ставятся внутри; с нуля — несколько минут, на облачной ВМ 1.5 мин)
docker build -f docker/Dockerfile -t metro-obstacle .

# 2. узел обнаружения (ждёт облако; топик лидара находит сам); результаты — в ./out
docker run --rm --net=host --ipc=host -v "$PWD/out":/out metro-obstacle

# 3. в другом терминале — проигрывание записи
docker run --rm --net=host --ipc=host -v /путь/к/записи:/bag:ro \
    metro-obstacle ros2 bag play /bag --read-ahead-queue-size 10 --delay 3 --wait-for-all-acked 5000
```

При старте узел пишет, что включено: `ускорения: потоков на кадр 4,
процессов-помощников 3, numba да` (многопоточная обработка — по умолчанию в
образе). Дальше в терминале узла — строка на каждый кадр записи: ответ и время
его обработки. Узел обрабатывает **каждый кадр, ни один не пропускается**
(`queue=all`):

```
кадр 19: ПРЕПЯТСТВИЕ 55.6 м — 172 мс, в очереди 12
кадр 20: путь свободен (видно до 148 м) — 168 мс, в очереди 13
```

### Где результаты прогона

- **`./out/detections_<дата>_<время>.jsonl`** — журнал: на каждый запуск узла
  свой файл (папка `out` появляется рядом, в папке запуска `docker run`; файлы
  создаются от root). Строка JSON на кадр: `frame` — номер кадра, `detected`,
  `distance` — до ближайшего препятствия, м вдоль пути, `confirmed` — все
  подтверждённые, `limit` — до скольких метров построен путь, `proc_ms` — время
  обработки, `latency_ms` — задержка ответа, `backlog` — кадров в очереди.
- Итог прогона — сколько кадров пришло и обработано, время обработки, где
  найдено препятствие:
  `python3 scripts/demo_summary.py out/detections_<дата>_<время>.jsonl`.
- Узел останавливается Ctrl+C — после того как разобрал очередь (в строке
  последнего кадра нет «в очереди»).

Если кадр обрабатывается дольше периода лидара (100 мс), кадры ждут в очереди,
и ответ отстаёт от записи («в очереди N»); после конца записи узел дорабатывает
очередь. Для работы на поезде, где важна задержка, — `queue:=latest` (берётся
самый свежий кадр, задержка не растёт).

`--net=host --ipc=host` обязательны: кадр весит ~24 МБ, при 10 Гц он идёт между
контейнерами через общую память DDS, а не по сети.
`--read-ahead-queue-size 10`: плеер Humble сначала заполняет очередь чтения
(по умолчанию 1000 сообщений — вся запись) и отдаёт первые секунды залпом.
`--delay 3`: плеер и узел успевают найти друг друга до первого кадра — иначе
первые кадры записи до узла не доходят. `--wait-for-all-acked 5000`: плеер не
выходит, пока узел не получил последний кадр.

То же через docker compose:

```bash
docker compose build
docker compose up detector                                   # узел; журнал — output/ros/detections.jsonl
BAG=/путь/к/записи docker compose run --rm player            # проигрывание
BAG=/путь/к/записи docker compose run --rm offline           # разбор записи целиком, без ROS-графа
```

### Визуализация (RViz2 в браузере)

```bash
docker build -f docker/Dockerfile --target viz -t metro-obstacle-viz .
docker run --rm --net=host --ipc=host metro-obstacle-viz     # http://127.0.0.1:6080/vnc.html
```

Порт слушается только на `127.0.0.1`; с удалённой машины —
`ssh -L 6080:127.0.0.1:6080 <машина>`. В сцене: прореженное облако, коридор
габарита (зелёный — путь свободен, красный — препятствие), рамка препятствия с
расстоянием и надпись `OBSTACLE 55.8 m` / `CLEAR to 140 m`. Система координат
сцены — `lidar_livox` (реальные записи); для синтетики — `FIXED_FRAME=hesai_lidar`.

### Видео работы

Ролик (~8 мин): живой прогон в Docker — `ros2 bag play` → узел → RViz2 и ответ
узла на каждый кадр (синтетическая запись, 1274 кадра, каждый обработан), итог
прогона и GIF по всем 19 записям (6 реальных и 13 синтетических) — тот же
детектор, разбор каждого кадра. Собирается на облачной ВМ одной командой:
`FIXED_FRAME=hesai_lidar scripts/vm.sh video <запись> 0.4` (запись экрана
RViz2 — ffmpeg в образе `viz`, `VIZ_LAYOUT=video`), галерея GIF —
`scripts/vm.sh montage <папка GIF>`.

## Параметры

Параметры узла (`ros2 launch metro_obstacle detector.launch.py имя:=значение`):

| параметр | по умолчанию | что |
|---|---|---|
| `topic` | `auto` | топик облака. `auto` — сразу подписка на `/sensing/lidar/hesai128/pointcloud` и `/lidar_points`, плюс поиск любого `PointCloud2` (кроме `*_labeled`) |

| `preview_stride` | `10` | прореживание облака для показа; `0` — не публиковать |
| `log_file` | `/out` (в образе) | журнал JSON Lines по кадрам; папка — свой файл `detections_<дата>_<время>.jsonl` на каждый запуск |

Переменные окружения (в образе уже выставлены):

| переменная | в образе | что |
|---|---|---|
| `RAIL_WORKERS` | `4` | потоков на кадр; больше 4 не даёт выигрыша |
| `RAIL_PROCESS` | `1` | логика на Python — ещё в 3 процессах |
| `RAIL_JIT` | `1` | скомпилированный numba перебор ступенек стен; `0` — прежний код на numpy (ответ тот же) |

Пример:
`docker run --rm --net=host --ipc=host -v "$PWD/out":/out metro-obstacle ros2 launch metro_obstacle detector.launch.py queue:=latest log_file:=/out`.

## Алгоритм

**Какую проблему решает.** Тоннель однообразен, препятствия редки, разметки
почти нет. Вместо классификатора объектов — точная геометрия пути и габарит
вагона вдоль него. Всё, что заходит в габарит, — помеха движению.

**Данные.** Один лидар (Hesai, 128 каналов), облако ~920 тыс. точек на кадр,
10 Гц. Глубина вдоль тоннеля — ось −y лидара.

**Обработка кадра.**

1. **Вид сверху.** Облако растеризуется в сетку 0.1 × 0.5 м. По контрасту
   высот находятся кромки тоннеля полосами глубины. Ось ведётся от ближних
   полос к дальним. Одна форма (полином до 3-й степени) описывает обе стены
   сразу, с учётом того, что за поворотом внутренняя стена заслонена
   (docs/knowledge.md §26, §31).
2. **Путь и стены одной кривой.** Путь — профиль кривизны по длине. Стены —
   отступы от пути по нормали, до двух ступенек (платформа, ниша). Вблизи путь
   держат рельсы. Узлы пути привязаны к тоннелю и сдвигаются на Δs. На каждом
   кадре две гипотезы — «память» (прошлый путь) и «заново» — и выбирается
   лучшая (§31).
3. **Δs** — продольный сдвиг между кадрами по профилю плотности вдоль пути,
   после вычета рисунка, стоящего на лидаре (§36).
4. **Высота.** Пол вблизи, крен и уровень головок рельсов по самим рельсам
   (§25). Профиль пути по высоте вдали строится по своду и полу (вид сбоку,
   §34); пол берётся относительно своего же уровня на 15–35 м (§36).
5. **Габарит.** Кузов 81-717: ±1.335 м, до 3.65 м над головками. Ниже 0.5 м —
   ±1.1 м (вырез под контактный рельс). Низ — 0.10 м над головками на всех
   дальностях. Бока и верх вдали сжимаются на погрешность пути:
   0.008·(D − 40) м. Предел обзора — там, где гипотезы пути «память» и
   «заново» расходятся больше чем на 0.3 м (§34).
6. **Скопления.** DBSCAN в угловых координатах лидара. Порог — половина
   ожидаемого числа лучей на предмет 0.25 × 0.25 м на этой дальности (не
   меньше 3); у предмета, стоящего на пути, в счёт идёт только его часть выше
   низа габарита — так видны и низкие предметы на рельсах (§37). Плоский
   «налёт» — много точек в слое тоньше 0.25 м — отсеивается (§24, §34).
7. **Решение.** Каждое скопление ведётся в координатах тоннеля (путь + Δs) и
   подтверждается, если нашлось на своём месте в 3 из 5 последних кадров.
   Ответ — ближайшее подтверждённое, расстояние вдоль пути.

**Что влияет на результат:** габарит (размеры, запас на погрешность пути),
порог скопления, правило подтверждения (3 из 5), предел пути 150 м. Все
параметры выбраны по физике (паспорт вагона, шаг лучей лидара) и на наборе
разработки; отложенные записи мерились один раз (docs/knowledge.md,
§31–§37, §40).

## Эксперименты и результаты

Подробно, с неудачами и отвергнутыми вариантами, — [docs/knowledge.md](docs/knowledge.md).

**Дальность подтверждённого обнаружения** (замеры по кэшам всех записей,
`research/exp21_eval.py`):

| объект | дальность |
|---|---|
| блок 2 × 2 м посередине (New_synth) | **103 м** — с начала записи |
| блок 2 × 2 м сверху, низ 2.85 м (New_synth) | **130 м** |
| длинный низкий предмет на рельсах, 2 × 0.2 м (New_synth) | 100 м |
| предмет 0.3 м: посередине / на рельсе / с краю габарита (New_synth) | 63 / 59 / 52 м |
| рабочий на пути при выезде в двухпутный (8 синтетических записей) | 51–102 м, медиана 82 м |
| человек и предметы старой синтетики (box / human / human_diff) | 67 / 93 / 84 м — предел видимости лидаром по разметке |
| человек на `doubleT_obstacle` (реальная запись) | на 55.5–56.5 м, в 66 кадрах из 72 |
| коробка 0.15 м на рельсе там же | в 92 кадрах из 125 |

**Слепая проверка — новая синтетическая запись** (1274 кадра, 2.1 км, ~20
предметов в габарите; в разработке не использовалась, прогнана один раз без
изменения кода). Правда — точки разметки, попавшие в габарит вокруг истинного
пути по `/tf`:

| дальность до предмета | 0–25 м | 25–50 м | 50–75 м | 75–100 м | 100–150 м |
|---|---|---|---|---|---|
| кадров, где предмет найден | 85% | 96% | 90% | 69% | 35% |

Подтверждённых находок без предмета рядом — 0 из 999. Первое подтверждение —
обычно в нескольких метрах от дальности, с которой предмет вообще виден лидару
(до 137 м). Ось пути против истинной: медиана ошибки 3 см на 50 м, 10 см на
100 м.

**Ложные срабатывания:** 0 подтверждённых на чистых реальных записях
(платформа, гермозатвор, стрелка, `roundT_squareT…`) и их зеркальных копиях, на
синтетике — 1 кадр (New_synth) и 0 на новой синтетической записи. Исключение — раструб
двухпутного тоннеля (`roundT_doubleT`, 24 кадра из 252, зеркально — 22). Там
путь ошибается вбок на 0.3–0.5 м, и обе гипотезы пути ошибаются согласно
(§34, §36).

**Скорость** (4 потока + процессы; живой поток — узел в Docker, `ros2 bag play`
в темпе записи 10 Гц):

| машина, запись | обработка кадра, медиана | живой поток 10 Гц, `queue=all` (по умолчанию) |
|---|---|---|
| Apple M4, реальная (~920 тыс. точек) | 78 мс | — (быстрее периода лидара: без очереди) |
| облако Intel Ice Lake 3.0 ГГц, реальная `doubleT_obstacle` | 166–170 мс (p95 218) | обработаны все пришедшие кадры (200–201 из 201); очередь к концу 20-секундной записи — до ~115 кадров, задержка ответа — медиана 7.5 с, максимум 20 с |
| облако, синтетика (307 тыс. точек, 1274 кадра) — строго по «Быстрому запуску» на чистой ВМ | 133 мс | все 1274 кадра пришли и обработаны, ответ совпал с Mac кадр в кадр; очередь к концу 127-секундной записи — до 385 кадров, задержка — медиана 27 с, максимум 53 с |

С `queue:=latest` на том же облаке задержка ответа не растёт (≈ времени
обработки), но обрабатывается 40–53% кадров. Ответ узла в контейнере под Linux
совпал с разбором на Mac кадр в кадр (1274 из 1274 на синтетике, §40).

Как менялась скорость: 280 мс → 97 мс (M4, §35: векторизация, потоки,
процессы) → 78 мс (§38–§39: повторы убраны, перебор ступенек стен в numba). На
каждом шаге ответ проверялся на совпадение кадр в кадр на 15 записях и на
замороженных итоговых (`research/exp_speed.py check`). Стенд (i7-9700E) не
мерили.

**Сложные ситуации:** раструб двухпутного (ложные), тонкие предметы (шнур 5 см
не виден: порог рассчитан на 0.25 × 0.25 м), низкие предметы на рельсе (коробка
0.15 м — в 92 из 125 кадров, предмет 0.1–0.2 м на новой синтетике — в 2 из
17), предметы на самой кромке габарита (находятся не во всех кадрах), резкое
расширение тоннеля (новая синтетика, кадры 546–563: путь строится только до
20 м).

## Ограничения

- Путь строится до 150 м — дальше препятствия не ищутся.
- Тонкие (до ~5 см) предметы не видны; низкие (0.1–0.2 м) — не в каждом кадре.
- Раструб двухпутного тоннеля — ложные срабатывания.
- Узел обрабатывает каждый кадр. Где кадр обрабатывается дольше периода лидара
  (облачная ВМ: ~170 мс на реальный кадр при 100 мс), кадры ждут в очереди:
  ответ отстаёт на ~0.7 с за каждую секунду записи, очередь держит ~24 МБ на
  кадр. Для работы на поезде — `queue:=latest` (задержка не растёт, часть
  кадров пропускается).
- Первый кадр записи ROS 2 изредка не доставляет, даже с `--delay 3` (в 1 из 3
  прогонов).
- Запись с медленного диска (<240 МБ/с) играется медленнее реального темпа:
  плееру нужно читать 24 МБ × 10 Гц (плеер пишет `Message queue starved`);
  кадры при этом не теряются.
