# Обнаружение препятствий на пути поезда метро по 3D-лидару

Хакатон «Московский транспорт», кейс «Система обнаружения посторонних объектов
для беспилотных поездов в тоннеле метро по данным 3D-лидара» (ТЗ —
[docs/ТЗ_ДепТранспорта.pdf](docs/ТЗ_ДепТранспорта.pdf)).

ROS 2-узел принимает поток облаков точек лидара (`sensor_msgs/PointCloud2`) и на
каждый кадр отвечает: **есть ли на пути поезда препятствие и на каком
расстоянии** (вдоль пути, в метрах). Всё работает в Docker (Ubuntu 22.04 +
ROS 2 Humble).

**Идея.** Объекты не классифицируются. Узел строит по кадру геометрию тоннеля —
ось пути, стены, крен, профиль пути по высоте — и ставит вдоль пути габарит
кузова вагона 81-717. Препятствие — всё, что попало внутрь габарита и
удержалось на своём месте в тоннеле 3 кадра из 5. Такой подход не требует
размеченных примеров препятствий и одинаково ловит человека, коробку или блок.

## Быстрый запуск

Нужны Docker и папка записи ROS 2 bag (`metadata.yaml` + `.db3`).

```bash
# 1. сборка (все зависимости ставятся внутри; первый раз — несколько минут)
docker build -f docker/Dockerfile -t metro-obstacle .

# 2. узел обнаружения (ждёт облако; топик лидара находит сам)
docker run --rm --net=host --ipc=host metro-obstacle

# 3. в другом терминале — проигрывание записи
docker run --rm --net=host --ipc=host -v /путь/к/doubleT_obstacle:/bag:ro \
    metro-obstacle ros2 bag play /bag --read-ahead-queue-size 10
```

В терминале узла — строка на каждый обработанный кадр:

```
кадр 19: ПРЕПЯТСТВИЕ 55.6 м — 172 мс, пропущено 1
кадр 21: путь свободен (видно до 148 м) — 168 мс, пропущено 1
```

`--net=host --ipc=host` обязательны: кадр весит ~24 МБ, при 10 Гц он идёт между
контейнерами через общую память DDS, а не по сети.
`--read-ahead-queue-size 10`: плеер Humble сначала заполняет очередь чтения
(по умолчанию 1000 сообщений — вся запись) и отдаёт первые секунды залпом.

То же через docker compose:

```bash
docker compose build
docker compose up detector                                   # узел; журнал — output/ros/detections.jsonl
BAG=/путь/к/записи docker compose run --rm player            # проигрывание
BAG=/путь/к/записи docker compose run --rm offline           # разбор записи целиком, без ROS-графа
```

### Визуализация (RViz2 в браузере)

```bash
docker build -f docker/Dockerfile --target viz -t metro-obstacle-viz .
docker run --rm --net=host --ipc=host metro-obstacle-viz     # http://127.0.0.1:6080/vnc.html
```

Порт слушается только на `127.0.0.1`; с удалённой машины —
`ssh -L 6080:127.0.0.1:6080 <машина>`. В сцене: прореженное облако, коридор
габарита (зелёный — путь свободен, красный — препятствие), рамка препятствия с
расстоянием и надпись `OBSTACLE 55.8 m` / `CLEAR to 140 m`. Система координат
сцены — `lidar_livox` (реальные записи); для синтетики — `FIXED_FRAME=hesai_lidar`.

## Что публикует узел

| топик | тип | что |
|---|---|---|
| `/obstacle/detected` | `std_msgs/Bool` | есть ли подтверждённое препятствие |
| `/obstacle/distance` | `std_msgs/Float32` | до ближайшего, м вдоль пути от лидара; `NaN` — нет |
| `/obstacle/status` | `std_msgs/String` | JSON кадра: находки, предел обзора, время обработки, задержка, пропуски, частота прихода кадров |
| `/obstacle/markers` | `visualization_msgs/MarkerArray` | габарит, рамки препятствий, надпись — для RViz2 |
| `/obstacle/gauge_points` | `sensor_msgs/PointCloud2` | точки, попавшие в габарит |
| `/obstacle/cloud_preview` | `sensor_msgs/PointCloud2` | прореженное входное облако |

## Параметры

Параметры узла (`ros2 launch metro_obstacle detector.launch.py имя:=значение`):

| параметр | по умолчанию | что |
|---|---|---|
| `topic` | `auto` | топик облака. `auto` — сразу подписка на `/sensing/lidar/hesai128/pointcloud` и `/lidar_points`, плюс поиск любого `PointCloud2` (кроме `*_labeled`) |
| `variant` | `final` | вариант детектора. `low_rest_b0` — видит и низкие предметы на рельсах (коробка 0.15 м), но слепой проверки не прошёл |
| `queue` | `latest` | `latest` — берётся самый свежий кадр, задержка не растёт; `all` — все кадры по порядку (для замеров; запись проигрывать с `--rate` < 1) |
| `preview_stride` | `10` | прореживание облака для показа; `0` — не публиковать |
| `log_file` | — | журнал JSON Lines по кадрам |

Переменные окружения (в образе уже выставлены):

| переменная | в образе | что |
|---|---|---|
| `RAIL_WORKERS` | `4` | потоков на кадр; больше 4 не даёт выигрыша |
| `RAIL_PROCESS` | `1` | логика на Python — ещё в 3 процессах |
| `RAIL_JIT` | `1` | скомпилированный numba перебор ступенек стен; `0` — прежний код на numpy (ответ тот же) |

Пример:
`docker run --rm --net=host --ipc=host -v $PWD/out:/out metro-obstacle ros2 launch metro_obstacle detector.launch.py variant:=low_rest_b0 log_file:=/out/detections.jsonl`.

## Алгоритм

**Какую проблему решает.** Тоннель однообразен, препятствия редки, разметки
почти нет. Вместо классификатора объектов — точная геометрия пути и габарит
вагона вдоль него. Всё, что заходит в габарит, — помеха движению.

**Данные.** Один лидар (Hesai, 128 каналов), облако ~920 тыс. точек на кадр,
10 Гц. Глубина вдоль тоннеля — ось −y лидара.

**Обработка кадра.**

1. **Вид сверху.** Облако растеризуется в сетку 0.1 × 0.5 м. По контрасту
   высот находятся кромки тоннеля полосами глубины. Ось ведётся от ближних
   полос к дальним. Одна форма (полином до 3-й степени) описывает обе стены
   сразу, с учётом того, что за поворотом внутренняя стена заслонена
   (docs/knowledge.md §26, §31).
2. **Путь и стены одной кривой.** Путь — профиль кривизны по длине. Стены —
   отступы от пути по нормали, до двух ступенек (платформа, ниша). Вблизи путь
   держат рельсы. Узлы пути привязаны к тоннелю и сдвигаются на Δs. На каждом
   кадре две гипотезы — «память» (прошлый путь) и «заново» — и выбирается
   лучшая (§31).
3. **Δs** — продольный сдвиг между кадрами по профилю плотности вдоль пути,
   после вычета рисунка, стоящего на лидаре (§36).
4. **Высота.** Пол вблизи, крен и уровень головок рельсов по самим рельсам
   (§25). Профиль пути по высоте вдали строится по своду (вид сбоку, §34).
5. **Габарит.** Кузов 81-717: ±1.335 м, до 3.65 м над головками. Ниже 0.5 м —
   ±1.1 м (вырез под контактный рельс). Низ — 0.10 м над головками. Вдали
   габарит сжимается на погрешность пути: 0.008·(D − 40) м. Предел обзора —
   там, где гипотезы пути «память» и «заново» расходятся больше чем на 0.3 м
   (§34).
6. **Скопления.** DBSCAN в угловых координатах лидара. Порог — половина
   ожидаемого числа лучей на предмет 0.25 × 0.25 м на этой дальности (не
   меньше 3). Плоский «налёт» — много точек в слое тоньше 0.25 м — отсеивается
   (§24, §34).
7. **Решение.** Каждое скопление ведётся в координатах тоннеля (путь + Δs) и
   подтверждается, если нашлось на своём месте в 3 из 5 последних кадров.
   Ответ — ближайшее подтверждённое, расстояние вдоль пути.

**Что влияет на результат:** габарит (размеры, запас на погрешность пути),
порог скопления, правило подтверждения (3 из 5), предел пути 150 м. Все
параметры выбраны по физике (паспорт вагона, шаг лучей лидара) и на наборе
разработки; отложенные записи мерились один раз (docs/knowledge.md,
§31–§37).

## Эксперименты и результаты

Подробно, с неудачами и отвергнутыми вариантами, — [docs/knowledge.md](docs/knowledge.md).

**Дальность подтверждённого обнаружения** (вариант `final`):

| объект | дальность |
|---|---|
| блок 2 × 2 м посередине (New_synth) | **103 м** — с первого кадра записи |
| блок 2 × 2 м сверху, низ 2.85 м (отложенный) | **128 м** |
| предмет 0.3 м посередине | 63 м |
| предмет 0.3 м с краю габарита | 46 м |
| человек и предметы старой синтетики (box / human / human_diff) | 67 / 93 / 84 м — предел видимости лидаром по разметке |
| человек на `doubleT_obstacle` (реальная запись) | на 55.5–56.5 м, в 61 кадре из 72 |

**Ложные срабатывания:** 0 подтверждённых на всех чистых реальных записях
(платформа, гермозатвор, стрелка, `roundT_squareT…` — последняя отложенная) и
на синтетике. Исключение — раструб двухпутного тоннеля (`roundT_doubleT`,
~24 кадра из 252). Там путь ошибается вбок на 0.3–0.5 м, и обе гипотезы пути
ошибаются согласно (§34, §36).

**Скорость** (кадр ~920 тыс. точек, 4 потока + процессы):

| машина | обработка кадра, медиана | живой поток 10 Гц |
|---|---|---|
| Apple M4 | 78 мс | — |
| облако, Intel Ice Lake 3.0 ГГц, Docker | 157 мс | обработка ~170 мс, обрабатывается 43–53% кадров (86–106 из 200 в разных прогонах), задержка ≈ времени обработки |

Как менялась скорость: 280 мс → 97 мс (M4, §35: векторизация, потоки,
процессы) → 78 мс (§38–§39: повторы убраны, перебор ступенек стен в numba). На
каждом шаге ответ проверялся на совпадение кадр в кадр на 15 записях и на
замороженных итоговых (`research/exp_speed.py check`). Стенд (i7-9700E) не
мерили.

**Сложные ситуации:** раструб двухпутного (ложные), тонкие предметы (шнур 5 см
не виден: порог рассчитан на 0.25 × 0.25 м), низкие предметы на рельсе
(коробка 0.15 м: `final` не видит, `low_rest_b0` видит в 92 из 125 кадров).

## Ограничения

- Путь строится до 150 м — дальше препятствия не ищутся.
- Тонкие (до ~5 см) и низкие (до ~0.2 м) предметы — на пределе или не видны
  вариантом по умолчанию.
- Раструб двухпутного тоннеля — ложные срабатывания.
- На облачной ВМ узел успевает обработать около половины кадров. Подтверждение
  «3 из 5» набирается медленнее, чем при каждом кадре.
- Запись с медленного диска (<240 МБ/с) играется медленнее реального темпа:
  плееру нужно читать 24 МБ × 10 Гц.

## Разработка

```bash
python3 -m venv venv && source venv/bin/activate && pip install -r requirements.txt
cd research && export PYTHONPATH=..          # исследовательские скрипты — отсюда
python exp_far_eval.py --summary --variants final        # мерило обнаружения по кэшу
python exp_speed.py check --all --golden output/exp22_golden --variants final low_rest_b0
```

Правила: каждый эксперимент — план в `docs/experiments/`, итог — раздел
`docs/knowledge.md`; отложенные данные меряются один раз; ускорение не меняет
ответ. Для агентов — [AGENTS.md](AGENTS.md).
