# AgentReadme.md

Ориентир по репозиторию для агента (или человека), впервые открывшего проект.
Не дублирует `knowledge.md` — там подробная база знаний по данным и экспериментам,
здесь — карта "что где лежит и зачем".

## Задача

Хакатон «Московский транспорт»: по потоку ROS 2 `PointCloud2` от 3D-лидара
беспилотного поезда метро определять препятствие на пути и расстояние до него.
Подробности ТЗ — в [5. ДепТранспорта.pdf](5.%20ДепТранспорта.pdf) и
[knowledge.md §1-2](knowledge.md).

Текущий фокус работы — не детектор препятствий напрямую, а надёжная геометрия
тоннеля (стены, ось пути, кривизна), которая нужна как опора: препятствие
определяется как то, что пересекает габарит движения поезда, а без знания,
где проходят стены тоннеля на самом деле, "пересекает габарит" не с чем
сравнивать.

## Откуда берутся данные

Сырые данные **не в репозитории** — лежат на внешнем диске
`/Volumes/T7/Dataset/` (~33 ГБ, 6 ROS 2 bag'ов, `sqlite3`, один топик
`sensor_msgs/PointCloud2` на bag). Диск должен быть подключён локально; в
Docker-контексте путь передаётся флагом `--dataset`.

Bag'и (см. [knowledge.md §3](knowledge.md)):

| bag | сцена | кадров |
|---|---|---|
| doubleT_platform | платформа | 345 |
| roundT_doubleT | двухпутный тоннель | 252 |
| roundT_pressureGate_roundT | гермозатвор | 268 |
| roundT_squareT_pressureGate_squareT | гермозатвор + стрелки | 545 |
| squareT_platform_squareT_switch | платформа + стрелка | 877 |
| doubleT_obstacle | стоящий поезд на пути | 201 |

`doubleT_obstacle` — единственный bag с реальным препятствием; во всех
остальных пяти путь свободен ("чистые" сцены), и именно они используются
для отработки геометрии тоннеля. `rail_detection.DEFAULT_BAGS` перечисляет
пять чистых bag'ов; `doubleT_obstacle` в него намеренно не входит.

Формат точки (26 байт, little-endian): `x, y, z, intensity: float32`,
`ring: uint16`, `timestamp: float64`. Глубина вдоль тоннеля — это `-y` (ось Y
сенсора направлена назад). Подробности координат — [knowledge.md §4-5](knowledge.md).

### Пакет `rail_detection/`

| файл | что делает |
|---|---|
| `loader.py` | Чтение bag: `load_frame` (один кадр, пересканирует файл — дорого при многих вызовах), `iter_frames` (один проход, с шагом), `iter_selected_frames` (один проход, только нужные индексы кадров — быстрее всего для выборок), `frame_count` (число кадров без чтения сообщений) |
| `detector.py` | `find_groove_and_rails` — находит желоб между рельсами и сами рельсы в одном срезе по глубине (базовый геометрический признак, см. knowledge.md §13) |
| `tracking.py` | `robust_centerline` — сглаживание centerline по срезам одного кадра с отбраковкой выбросов |
| `curvature.py` | `fit_straight_or_arc` / `ransac_poly_fit` — RANSAC-подгонка прямая-или-дуга; `eval_fit`/`slope_from_fit` — единообразное вычисление по результату подгонки |
| `walls.py` | **Устаревшие** методы детекции стен (`find_wall_positions`, `combined_wall_fit`) — независимая детекция стены в каждом срезе координат сенсора. Оставлены для сравнения в `eval_tunnel_geometry.py --compare` |
| `plotting.py` | Графики для `run_rail_detection.py` (вид сверху, centerline, overlay по bag'ам) |
| `tunnel_frame.py` | **Текущий рабочий метод** (744 строки) — геометрия тоннеля в координатах пути. Подробно ниже |

## Текущий метод (rail_detection/tunnel_frame.py)

Развитие в два шага, оба задокументированы в `knowledge.md`:

**§15 — координаты пути.** Вместо независимой детекции стены в каждом срезе
(старый `walls.py`) — переход в криволинейные координаты `(d, u, v)`: `d` —
глубина, `u` — смещение вбок от оси пути (с поправкой на курс), `v` — высота
над головкой рельса. В этих координатах стена — почти прямая линия, а не
кривая, и обе стены подгоняются ОДНОЙ общей формой (прямая или дуга), что не
даёт им "разъезжаться домиком".

**§16 — увязка с рельсами + кусочная ширина.** Рельсы и стены решаются одной
системой МНК (рельсы держат ось вблизи, стены дают длинную базу для
кривизны), профиль пола строится по всей глубине или прямо из облака (если
рельсов нет — а такое бывает на сотнях кадров подряд), полуширина может быть
кусочно-постоянной (для станций, где граница — то торец платформы, то стена
за ним).

Главная функция: `fit_tunnel_geometry(points) -> dict | None` с ключами
`frame` (опора: ось, пол, колея), `shape` (общая форма — прямая/дуга, радиус),
`left`/`right` (геометрия каждой стены: полуширины, границы сегментов,
метрики `coverage`/`leak`). Служебные функции для рисования — `wall_x`,
`axis_formula`, `geometry_formula`.

**Метрика** (в `eval_tunnel_geometry.py`, НЕ "гладкость подгонки" как в
устаревшем `validate_geometry.py`): `coverage` — доля срезов, где предсказанная
стена реально совпадает с точками; `leak` — доля точек, оказавшихся ЗА
предсказанной стеной (усреднена по срезам, не по точкам — иначе доминирует
ближний план). Плюс `axis_holdout_error` — ошибка оси на рельсах, ОТЛОЖЕННЫХ
от подгонки (дальше 15 м), честная проверка того, что кривизна по стенам
действительно предсказывает путь.

## Как проверить результат

```bash
# метрика на 4 разработочных прогонах (dev_runs.json) с сравнением со старыми методами
python eval_tunnel_geometry.py --test-set dev_runs.json --compare

# слепая проверка на замороженном 5-м прогоне (не трогать до финального изменения!)
python eval_tunnel_geometry.py --test-set validation_run.json

# визуализация: сетка кадров с найденной геометрией
python plot_tunnel_geometry.py --test-set dev_runs.json --n-sample 40

# GIF целого прогона с лентой кривизны — качественная проверка на связности кадров
python make_run_gif.py --bags roundT_pressureGate_roundT
```

Все команды принимают `--dataset /path/to/Dataset`, по умолчанию
`/Volumes/T7/Dataset`.

## Договорённости по методике (важно не нарушать)

- **`validation_run.json` не используется при разработке** — только для
  финальной слепой проверки после того, как решение по алгоритму принято на
  `dev_runs.json`. Так же и `hidden_test_set.json` относительно `test_set.json`
  в предыдущей итерации (§15).
- Оценка идёт на **прогонах целиком**, а не на случайных кадрах — соседние
  кадры одной записи почти одинаковы, случайная выборка кадров утекает между
  разработкой и проверкой.
- Метрика привязана к точкам (`coverage`/`leak`), не к гладкости подгонки —
  гладкая кривая через неверные точки всё равно "гладкая".
