# Эксперимент 22. Скорость без повторов: те же вычисления, без лишних

**Задача (заказчик):** в живом потоке (ROS 2-узел, 10 Гц) кадр обрабатывается
~200 мс на облачной ВМ (Ice Lake 3.0 ГГц) и ~96 мс на M4 — узел берёт каждый
второй кадр, подтверждение «3 из 5» растягивается. Ускорить, **сохранив
качество ответа**. Сначала — Mac на разных записях, потом — облако.

**Статус: проведён, разбор — knowledge.md §38.** Шаг 1 (прямая оси раз на
полосу) принят: ответ тот же (Mac 15/15 в обоих режимах, итоговые 9/9, ВМ 7/7),
M4 145 → 139 мс, ВМ 294 → 275 (1 поток) и 203 → 191 мс (4 потока + процессы).
Шаг 2 откатан по отсечке (−4 мс). До 10 Гц далеко — нужны уровни 2–3.

**Ветка:** `feature/speed-exact` от `feature/ros2-docker` (c0ae9b7).
**Точка отсчёта:** тег `speed-exact-ref` — код до первой правки.

## Главное правило (как в §35)

Меняется только **реализация**. Ответ после каждой правки совпадает с эталоном
`speed-exact-ref` кадр в кадр: дискретное (выбор гипотезы, число ступенек,
скопления, находки) — точно, числа — до 1e-6 (`exp_speed.py check`). Не
совпал — правка откатывается.

Эталон `speed-ref` (§35) для этого не годится: он снят до §36 (другой Δs по
умолчанию). Новый снимается с текущего кода, Δs по умолчанию.

## Где время (профиль в один поток, 40 кадров `doubleT_obstacle`, мс/кадр)

| стадия | ВМ 2.0 ГГц | M4 |
|---|---|---|
| стены вида сверху (`run_silhouette`) | 100 | 40 |
| перебор ступенек стен (`search_steps`) | 71 | 22 |
| по точкам (координаты пути, габарит) | 66 | 32 |
| рельсы (`rail_samples`) | 27 | 12 |

Больше 2–4 потоков не помогает ни на M4, ни на ВМ (перебор 1–16 на ВМ:
229–243 мс) — упор в две последовательные стадии, обе — циклы Python из
мелких вызовов numpy.

## Гипотезы уровня 1 — повторы одного и того же расчёта

1. **`views.band_edges` → `_predict`:** ось предсказывается `np.polyfit` по
   истории полос для *каждой строки* растра; история меняется только между
   полосами. Коэффициенты — раз на полосу, значение `k·d + b` — на строку, той
   же формулой. Ожидаемо бит в бит.
2. **`parallel_path._search_side` → `_split_cost`:** кандидаты границы идут
   по сетке 2.5 м; соседние кандидаты между одними и теми же кромками дают
   одно и то же разбиение, а отрезки повторяются между кандидатами. Отрезок
   однозначно задан рангами границ среди отсортированных кромок; внутри —
   те же массивы в том же порядке (маска сохраняет исходный порядок).
   Запоминать итог отрезка по паре рангов — те же числа.
3. **Узел:** картинка для RViz2 — после ответа, в отдельном потоке (не
   конвейер; сверяется живым прогоном на ВМ, ответ не затрагивает).

Уровни 2 (numba на горячих циклах) и 3 (конвейер через кадр в двух процессах)
— отдельным решением после итога уровня 1.

## Риски

- Кэш отрезков по рангам неверен, если маска `(s >= lo) & (s < hi)` не
  совпадает с диапазоном рангов (равные s на границе) — проверить на
  совпадениях s с узлами сетки.
- Выигрыш уровня 1 может оказаться меньше оценки (~25 + 30 мс на ВМ) — тогда
  решение об уровнях 2–3 принимается по фактическому профилю.
